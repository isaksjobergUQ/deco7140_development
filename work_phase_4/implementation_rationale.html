Implementation Rationale

Key decisions and evidence for WP4: how the build meets client goals, user needs, WCAG 2.2, and ethical design.

Alignment with Client & User Needs

Client mission (CCI): The site supports social cohesion by helping international students connect, share, and access resources. Community features (forums/study groups), event discovery, and clear tips directly target transition challenges.

User needs (from WP1–3): Academic support (filterable tips, study groups), living help (housing/transport/daily-life tips), social connection (events + forums), and cultural adaptation (language help + culture content). Multi-language UI (EN/ZH) and plain language writing reduce cognitive load for non-native speakers.

Variations from A3 & Justifications

  • Horizontal cards vs. accordions (Community): Immediate scanability and mobile swipe improve discovery and reduce clicks; matches familiar social feeds.
  • Dedicated Contact page: Clear IA and focused task completion; easier to find on mobile.
  • Unified headers: Consistent hierarchy lowers cognitive load and simplifies maintenance.
  • User posts (localStorage) vs. static threads: Increases engagement and demonstrates dynamic state without backend risk.
  • Logo added: Instant brand recognition for an international audience.
  • 3 featured events on Home: Higher information density with controlled complexity; less scrolling than a single hero event.

Accessibility (WCAG 2.2 AA)

  • Perceivable: Semantic headings (h1–h3), alt text for images, decorative images marked with empty alt. Color tokens ensure ≥4.5:1 body/≥3:1 large text contrast.
  • Operable: Full keyboard access, visible focus, skip-link, 44×44px touch targets, no timing constraints.
  • Understandable: Plain language, consistent labels/menus, helpful labels/placeholders and inline validation.
  • Robust: Valid HTML5 landmarks (header/nav/main/section/footer); ARIA only where needed.

Ethical Considerations

Subscription plug-in: Not implemented. Core content remains free to avoid exclusion and data risk. Only non-sensitive preferences are stored locally (bookmarks/likes), aligning with public interest and inclusivity.

Cultural sensitivity: Neutral, inclusive language; diverse examples; bilingual microcopy for common actions.

Privacy: No server-side PII collection; localStorage only, with clear purpose explained in-UI.

Implementation Challenges & Strategies

  • Horizontal scroll affordance: Scroll-snap + subtle cues; tested on mobile to ensure discoverability.
  • State without backend: Small localStorage module (bookmarks/likes/user posts) to persist interactions.
  • Efficient rendering: ES modules, event delegation, and targeted re-renders on filter changes.
  • Mobile nav clarity: Emoji icons with aria-label, active state, and consistent order.

API Integration

Reusable GET/POST modules (js/modules/getData.js, postFormData.js) with fetch() + FormData. Community posts use the Generic Chat endpoint; required headers (student_number, uqcloud_zone_id) are included for both POST and GET to ensure reliable reads in deployment. Contact form uses the Simple Community endpoint with graceful localStorage fallback.

Accessibility Audit

Audited with IBM Equal Access Accessibility Checker. Key fixes: moved aria-label from decorative spans to anchors in mobile nav; increased contrast for nav/footer text; verified all interactive controls have accessible names. Violations dropped from 28 to near-zero on tested pages.

Code Quality & Deployment

  • Structure: Modular CSS (tokens/utilities/components/pages) and ES6 modules; semantic HTML throughout.
  • Version control: Regular, descriptive commits documenting incremental changes.
  • Deploy: UQCloud zone → /work_phase_4; homepage index.html.
  • Repo: GitHub

Conclusion

The build faithfully realises the A3 concept, with targeted variations that increase usability and inclusivity. It aligns with CCI's goals, addresses user needs, integrates WCAG 2.2 AA practices, and demonstrates ethical restraint around data and access.
